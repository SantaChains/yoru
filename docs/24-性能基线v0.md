## 1. 方法论（网络调研采纳）

信源：hyperfine/criterion 惯例、benchmarking-specialist 纪律清单、cursa「Benchmarking Discipline」协议。采纳要点：

1. **预热丢弃**（2 次，含文件系统缓存与进程冷启动）
2. **多次采样报分布**（7 次，报 min/median/max + spread%，不报均值——长尾敏感）
3. **输出校验**（checksum 逐位比对双方，快而错不算数；同时防死码消除）
4. **启动开销对照组**（空脚本，分离「解释器执行」与「进程+管线开销」）
5. **同机同载**（顺序执行同一 harness，披露环境）
6. **诚实对比纪律**：用对方推荐配置（LuaJIT 默认 JIT on）、报告落败项、发布完整 harness（`benchmarks/sort/` 三件套入库）、注明日期版本

**环境**：Windows 11 / Git Bash，`yoru 0.1.0` release（rustc stable，MSRV 1.82）/ LuaJIT 2.1.1788460057（scoop main）/ QuickJS 2026-06-04 + quickjs-ng 0.17.0（scoop main，均直接 exe 路径排除 shim 开销）/ Python 3.13 计时 harness（`time.perf_counter` 墙钟）。

## 2. 工作负载规格

- **N = 3000** 整数，公式生成 `xs[i] = (i * 2654435761) % 100000`（Knuth 乘法散列）——不用 LCG 的原因：map/lambda 面无外部状态注入，公式生成使双方数据**逐位一致**且 O(1)/元素（2^53 内 double 精确，LuaJIT 无精度问题）
- **标准移位插入排序**（while + break + 下标赋值），O(n²/2) ≈ 450 万次内层操作
- 输出 `sum, xs[0], xs[n-1]` 校验
- 对照组：空 main（分离启动）

## 3. 结果（2026-10-12）

| 指标 | Yoru T1 VM | LuaJIT 2.1 | 说明 |
|---|---|---|---|
| 全程 median | 737.4 ms | 87.2 ms | 含启动 |
| 启动（空脚本） | 32.0 ms | 76.7 ms | Yoru 胜：无 JIT 编译，32ms = 进程+parse+typeck+lower+verify |
| **净执行** | **~705 ms** | **~10 ms** | **~70x** |
| spread | 8.0% | 27.0% | LuaJIT 波动大（JIT 编译抖动） |

**诚实结论**（按对比纪律报告落败项）：
- **70x 落后于 LuaJIT，预期带内且无羞耻**——LuaJIT 是 tracing JIT 顶级实现（Mike Pall），T1 是朴素栈式解释器（无 JIT/AOT/内联缓存）。解释器 vs JIT 的经验差距带 10-100x。
- Yoru 的相对优势面恰在**启动**（32ms vs 77ms）与三限沙盒——与优先级排序一致：编译/加载快是承诺项，执行速度当前非承诺项。
- 基线价值：后续每阶段（寄存器 VM、内联缓存、AOT、超时指令融合）以此表回归对照，不凭感觉。

## 3.1 QuickJS 对照（2026-10-12 补测）——**同类参照，价值高于 LuaJIT 对照**

QuickJS 是**纯解释器**（无 JIT），与 T1 同类——这是比 LuaJIT 更公平的参照系。`bench_qjs.js` 与 Yoru/Lua 严格同构，checksum 逐位一致。ng 走直接 exe 路径（scoop shim 实测虚增 ~30ms 启动，已排除）：

| 指标 | Yoru T1 VM | LuaJIT 2.1 | QuickJS 原版 | quickjs-ng 0.17.0 |
|---|---|---|---|---|
| 全程 median | 737.4 ms | 87.2 ms | **133.7 ms** | 246.4 ms |
| 启动（空脚本） | 32.0 ms | 76.7 ms | **25.0 ms** | 31.2 ms |
| **净执行** | **~705 ms** | **~10 ms** | **~109 ms** | **~215 ms** |
| 相对 Yoru | 1x | 70x | **6.5x** | 3.3x |

**结论修正**：
- **6.5x（对 QuickJS 原版）才是 Yoru 当前的真实坐标**——同为纯解释器，差距来自内联缓存/指令分派密度/值表示等实现质量，而非 JIT。这把「短期可追赶带」从幻想（追 JIT）拉回现实（追顶级解释器），阶段 5 寄存器 VM + 内联缓存的目标即此。
- **意外数据点**：原版 Bellard QuickJS 净执行比社区活跃分支 ng **快 ~2x**（109 vs 215ms）——「活跃 = 更快」不成立，ng 的取舍偏向正确性/特性。选参照物要看实测不看声望。
- 启动四者同带（25-32ms），LuaJIT 反而最慢（77ms，JIT 初始化）——Yoru「启动快」承诺面在同类解释器中无优势也无劣势，真正差异点仍在沙盒与错误面。
- 教训沉淀：**对照组选型至少覆盖两类**（JIT 上限参照 + 解释器现实参照），单点对照会系统性误判坐标。

## 4. 基线发现 #1：SetIndexLocal（决策 80）

首测 0.15s 撞爆 64MB 堆限额——根因：通用 `SetIndex` 弹出的栈上容器副本与局部槽**双重引用**，决策 13 的 `refcount==1` 互斥判定对局部数组恒不成立 → 每次下标赋值 O(n) 整表拷贝 + 累计计账（~108GB）。

修复：新 opcode `SetIndexLocal 0x66`（lower 快路径：base 为局部变量 plain Assign；VM 臂槽位值暂出→原地变异→回填）。语义不变（真别名仍走拷贝），错误必终止 run 无需还原槽位。修复后 1.1s→0.70s 且归一。

**方法论教训**：性能基线要在**功能稳定后、冻结前**建立——这个缺陷若无真实负载永远不会浮出（现有 114 测试全是正确性断言，无性能断言）。
