# 13 原生编译执行与语言家族调研（设计14 输入）

[目录](README.md)

> 状态：调研定稿。本文档承接用户 2026-10-11 输入的方向调整：**在安全、速度、性能、编译快、热重载、JIT、AI 错误少、效率、占用九个维度上重新取舍；学习 Lua 简洁内核，但偏向原生编译执行（TS 外观不变）；参考 Meta Flow；充分调研函数式家族、Lisp、Pascal；学习 LLVM 后端与编译原理、VM 内核。**
> 所有外部数据均已网络核实，来源标注在各节。与既有设计冲突处，本文档给出修订建议，不直接推翻已定稿决策（修订需走 11-决策记录 流程）。

## 13.0 方向调整的核心判断

用户输入把「原生编译执行」从「分阶段未来方向」升格为**一等设计目标**。这动摇了 05-后端取舍 §5.1「MVP 不做 AOT/JIT」的时间表，但不动摇其架构决策——恰恰相反，已有决策（字节码为权威格式、Cranelift 主后端、禁止 JIT 锁死语言演进）正是原生编译路线的正确地基。本轮调整的是**优先级与路线图**，不是执行模型。

九维优先级向量（用户输入整理，按声明顺序）：
安全 > 速度/性能 > 编译快 > 热重载 > JIT > AI 错误少 > 效率高 > 占用少。

**关键耦合**：编译快不再只是体验指标，而是三个上游目标的使能条件——
1. **热重载 × 原生执行**的张力只能靠编译快化解：reload = 重新编译模块到原生码，编译慢则热重载必须退回解释执行（Luau 走的就是这条路，见 13.2）；
2. **AI 错误少**依赖「生成→编译→JSON 诊断→修复」闭环的迭代速度，编译慢则闭环慢；
3. **加载时 AOT**（插件场景的默认形态）要求编译开销 ≤ 毫秒级每千行。

## 13.1 执行栈路线：四层模型（修订 05 §5.2）

原设计为「解释器（MVP）→ 单层 JIT（P2）」。按新方向修订为四层，每层可独立裁剪：

| 层 | 机制 | 编译延迟 | 代码质量 | 复杂度 | 定位 |
|---|---|---|---|---|---|
| T1 | 寄存器式字节码解释器（Lua 5.4/Luau 风格） | 0（复用编译产物） | 基线 | 低 | **通用兜底层**：WASM/移动/无 codegen 平台、沙盒回退、启动零延迟路径 |
| T2 | 加载时 AOT（Cranelift，模块级） | 毫秒级/千行 | 好（比 LLVM 慢 2-14%） | 中 | **默认原生层**：桌面/服务器加载模块即编译，产物按源哈希缓存 |
| T3 | 热点函数优化 JIT（Cranelift + 类型特化） | 函数级 | 好 | 中 | 长运行进程的热点加速，静态类型消除大部分 guard（09 §9.1 已记录） |
| T4 | 发布 AOT（可选 LLVM/inkwell） | 秒级 | 最优 | 高（依赖重） | 发布产物、离线批量编译，不进运行时依赖 |

**T2 是本轮新增的核心**：加载时编译而非运行时热点触发。理由：
- 插件/嵌入场景每个模块只编译一次、缓存永久复用（字节码缓存 qjsc 模式 + 原生缓存双键），冷启动成本被摊销为零；
- 与热重载兼容：reload 即重新编译该模块（T2 编译速度使这成为用户不可感知的操作）；
- 避免 T3 的复杂度前置（guard/snapshot/deopt 基础设施）。

### 后端选型数据（已核实）

| 后端 | 体量 | 编译速度 | 代码质量 | 依赖/集成 | 判定 |
|---|---|---|---|---|---|
| Cranelift | ~7 万行 Rust | 比 LLVM 快 4-5 倍（Wasmtime 实测 425-434%；rustc 后端实测 3-5 倍） | 慢 LLVM 2-14%（Kōdo 9-17% 一致） | Rust 原生、ISLE 指令选择、对恶意输入硬化、无 UB | **主后端（维持 05 决策）** |
| MIR (vnmakarov) | ~1 万行 C，目标文件 170KB | 比 GCC 快 ~100 倍 | GCC -O2 的 ~70% | C 库，需 unsafe FFI 桥 | **备选记录**：占用敏感场景可评估；与「VM 纯 Rust」承诺冲突，仅作 fallback 档 |
| copy-and-patch | 模板 + 打补丁器 | ~µs 级（比 LLVM -O0 快 100 倍，-O2 快 1000 倍） | 好（每 stencil 由 LLVM 构建期优化） | 构建期依赖 LLVM 提取 stencil，运行期零依赖 | **暂不采用**：CPython 需要专用 DSL 生成解释器 + clang 提取；Rust 工作流下 stencil 提取工具链成本高，收益被 T2 覆盖。留档为 T1.5 候选（来源：Xu & Kjolstad 2021；CPython PEP 744，3.15 实测比解释器快 5-12%） |
| LLVM (inkwell) | ~2000 万行 | 慢 | 最优（LTO/向量化/PGO） | 构建与体积代价高 | T4 发布专用（维持 05 决策；Zig 自研 debug 后端 + 保留 LLVM release 的同款模式已是行业共识） |

## 13.2 语言家族调研（按家族归纳取舍）

### Lua / LuaJIT / Luau（内核简洁的范本，维持为第一参照）
- Luau 现状（luau-lang.org/performance）：解释器优先——因为 JIT 在其目标平台并非全可用；`--!native` 模块级 AOT 编译发货代码，数学密集循环提速 2-4 倍；JIT 只在 x64/arm64 可用，且**只用类型注解特化、不做运行时类型分析**；编译吞吐 95 万行/秒/单核。
- 对 Yoru 的直接启示：(a) **解释器必须永远是完整可用的第一公民**（跨平台与沙盒回退），原生层是加速而非前提；(b) Luau 的「静态类型特化、无运行时推断」路线与 Yoru 的渐进类型完全同构——Yoru 的 T2/T3 可以更激进，因为 Yoru 的 strict 模式全类型化后特化无需 guard；(c) 95 万行/秒是可引用的编译吞吐基准，Yoru 应把「≥100 万行/秒字节码编译」设为发布门槛。

### Pascal 系（Wirth 单遍纪律 → 编译快的本源）
- Wirth 线（PL/0→Pascal→Modula-2→Oberon，来源：sgeos 编译器流式系列、Project Oberon）：单遍递归下降 + 声明先用后解析 + 语言规格小到可放进工作记忆，Oberon 编译器约 4000 行；Turbo Pascal 快的一半功劳是「语言本身被设计成可单遍编译」（来源：Hacker News Turbo Pascal 40 周年帖，Anders Hejlsberg 实现细节）。
- **采用（写入 02/12 修订）**：
  1. **流式编译纪律**：lexer→parser→typeck→codegen 按声明粒度流水推进，模块内不做全程序 AST 物化；工作内存 O(最大单声明)，不是 O(程序)。
  2. **顶层两遍、函数体单遍**（Go 模式）：模块顶层先收符号表再编译（AI 生成代码的定义顺序不受惩罚——这点对 AI 错误少维度关键，纯 Wirth 单遍的声明先用会让 AI 排序错误率上升），函数体内保持单遍。
  3. 语言规格保持「一页纸」纪律：02 的 BNF 已经很小，任何新增语法必须连带评估单遍可编译性。

### Lisp 家族（Janet 为主要参照）
- Janet（janet-lang.org）：整个语言（核心库+解释器+编译器+汇编器+PEG）300-500KB；核心仅 8 个特殊形式（do/def/var/set/if/while/break/fn），其余全部由宏提供——**极简内核 + 宏 = 可扩展性**的 Lisp 公式；字节码可由汇编器**验证**（register VM，LuaJIT 式编码 + 结构校验）；image 格式可把编译期值（含闭包）序列化进运行时。
- 对 Yoru 的取舍：
  - **采用**：(a) **字节码结构化验证器**（见 13.3 安全节，这是本轮最重要的安全补强）；(b) image 思想→Yoru 的 LBC0 已是持久化格式，补「模块级 image 缓存 = 字节码 + 迁移钩子状态」，服务热重载；(c) Janet 的 mutable/immutable 双轨集合（array/tuple、table/struct）——Yoru 的 `let`/`let mut` 已是同构思想，标准库按此分层（不可变集合为默认 API 面）。
  - **不采用**：宏系统（01 非目标维持；宏把「编译快」变成不可预测——宏展开耗时无上界，与流式编译纪律冲突；AI 生成宏的错误率也显著更高）。表达力缺口改由「泛型 + 高阶函数 + 过载」承担（见 13.5）。

### 函数式家族（Roc / Koka / ML 系）
- Roc（roc-lang.org）：值语义 + 引用计数 + **引用计数为 1 时机会性原地变更**——纯函数语义拿到命令式性能；编译器全量推断、无 GC；错误信息以「友好」为一等目标；平台架构（标准库纯、I/O 由平台注入）与 Yoru 的能力注入同构。Roc 编译器 2025 起从 Rust 重写为 Zig，动因同样是编译吞吐。
- Koka/Perceus（09 §9.3 已记录）与 Roc 验证了同一条路线：**值语义不必付拷贝代价**。
- **采用（升级优先级，修复 12.2 的语义矛盾）**：List/Map 的 P1 实现路线从「COW」具体化为 **refcount==1 原地变更**（Roc/Koka 模式）：值语义是语义承诺，拷贝消除是编译器义务。这同时解决了 12.2 `Value` 定义里 `Rc<RefCell>` 引用语义与决策 6 的矛盾——RefCell 退为内部实现细节，语义层不可观测（单线程 VM 内无别名逃逸）。
- **采用**：Roc 的 `!` 效果后缀思想降级评估为 P2——Yoru 用 Result + async 语法糖已覆盖 MVP，但「纯函数不可调用副作用宿主函数」可以用 HostSig 的 purity 标记低成本达成（宿主函数声明是否纯，typeck 据此拒绝在纯上下文调用），这对沙盒审计是免费收益。

### Meta Flow（类型系统参照）
- Flow 现状（handwiki/2026 对比）：比 TS 更严格更完整（默认空值检测 98% vs TS strict 87%）、2020 重构后类型检查提速 6 倍、exact object types 默认开启；但生态萎缩（npm 类型覆盖 12% vs TS 94%），Meta 已降级投入。
- 对 Yoru 的取舍：
  - **维持** 03 §3.3 已确认的「Flow 风格结构子类型」；Flow 的 exact object types 默认收紧与 Yoru 的 struct 固定形状天然一致。
  - **采用（P1）**：**流式收窄（flow-sensitive refinement）**——Flow/Luau 都以此为核心竞争力（`if x != nil { x: T }`），对 AI 生成代码的错误率收益最大（AI 最常见的类型错误是未收窄的 Option/联合类型）；strict 模式必配。
  - **教训（写入 11 备忘）**：健全性主张如果没有工具链与生态支撑就是负债。Yoru 的 JSON 诊断/修复建议/LSP 不是附属功能，是类型系统价值兑现的**前提**——这正是 Flow 输给 TS 的地方，不是类型系统本身。

## 13.3 安全增补：字节码结构化验证器（本轮最重要的补强）

04 §4.5 目前只有 CRC32 校验——CRC 只防**损坏**，不防**恶意**。一旦 LBC0 成为插件分发格式（市场安装、跨端同步），恶意构造的字节码（非法 opcode、越界跳转、栈深不变量破坏、upvalue 描述符伪造）可以直接攻击 VM。

**新增决策（建议编号 9）**：LBC0 加载必须通过结构化验证器，通过前不得进入执行：
1. opcode 值域合法 + 操作数模式匹配（A/sA 形态与 opcode 组一致）；
2. 全部跳转偏移落在函数原型指令流边界内、目标为指令起始；
3. 编译期最大栈深声明与指令流静态重算一致（QuickJS 同款不变量，加载期复算）；
4. upvalue/常量池/原型索引全部在界内；
5. CRC32 仍保留（损坏检测），验证器在其后。

参考：Janet 字节码汇编器验证、WASM validate-before-instantiate（Wasmtime 的防恶意输入硬化正是 Cranelift 被选为主后端的安全论据）。此验证器同时是 fuzz 主战场（10 §10.2 第四层 fuzz 的直接靶子）。

## 13.4 LLVM 后端与编译原理要点（学习纪要，供 T4 实现）

- **SSA 是一切的基础**：LLVM IR/Cranelift CLIF/QBE/MIR 全部是 SSA。Yoru 的提升路径（05 §5.4：栈式字节码→flatten+SSA→CLIF）方向正确；block params 优于 phi（Cranelift 风格），提升器实现更简单。
- **优化管线的性价比排序**（对脚本语言）：mem2reg/常数传播/死代码消除 ≫ 内联 > 循环优化 ≫ 向量化。脚本语言热点在调用与分配，不在向量化——T2/T3 不做向量化，留给 T4。
- **寄存器分配**：Cranelift 线性扫描（快、质量可接受）是脚本语言正确选择；LLVM 图着色（PBQP）是发布路径的奢侈品。
- **依赖成本量化**（已核实）：rustc_codegen_cranelift 使 codegen 时间降 ~20%、全量构建降 ~5%（2025 正式目标：debug 构建生产可用）；Zig 自研 x86-64 后端 wall-clock 快 5-50%，但 release 仍交 LLVM——**「快路径绕开 LLVM、发布路径保留 LLVM」是 rustc/Zig/Yoru（T2 vs T4）共同收敛的产业结构**。
- **调用约定**：CPython JIT 后续优化的 ghccc（定制调用约定减少帧操作）提示 T3 可为「脚本函数间调用」定义 Yoru 专用调用约定（寄存器传参 + 尾调用友好），这是解释器→JIT 增益的最大单项来源之一。

## 13.5 表达力与可扩展性（长期方向的补强）

「有一定表达能力、可拓展」按成本递增排序的路线（全部保持内核小、无宏）：
1. **P0**：高阶函数 + match + ADT（已在设计内）。
2. **P1**：流式收窄（13.2 Flow 节）+ 运算符过载（struct 实现算术协议，游戏数学刚需：Vec3 + Vec3）——以协议约定而非 C++ 式任意重载，编译期解析、零动态分派。
3. **P1**：宿主命令注册（12.2 `#[l_command]`）+ 标准库分层导入——Lua「内核小、能力交给库」哲学的正式化。
4. **P2**：效果标记（13.2 Roc 节）+ 尾调用优化（T1 显式调用栈上 TCO 有限制，严格尾调用仅保证自尾调用；寄存器 VM 改造后对齐 Lua 5.4 的 RETURN 快路径）。
5. **不做**：宏、类型级元编程、继承（01 非目标维持——Janet 证明扩展性可以不靠宏，Roc 证明表达力可以不靠继承）。

## 13.6 九维取舍矩阵（执行策略对比）

| 维度 | 纯解释器 | +T2 加载时 AOT (Cranelift) | T3 优化 JIT | T4 LLVM 发布 |
|---|---|---|---|---|
| 安全 | 高（无 codegen 攻击面） | 高（Cranelift 硬化 + 验证器前置） | 中高（deopt/guard 复杂度） | 高（离线，不在攻击面内） |
| 速度（启动） | 最优 | 依赖缓存，首载毫秒级 | 同左 | 编译期完成，最优 |
| 性能（峰值） | 基线 1× | 2-4×（Luau native 量级） | 3-8× | 3-10× |
| 编译快 | 最优 | 毫秒级/千行 ✓ | 函数级 | 秒级 ✗（仅发布） |
| 热重载 | 最优 | ✓（重编译毫秒级） | 需失效协议 | ✗（不适用） |
| JIT 需求 | 无 | 无（加载时） | 有 | 无 |
| AI 错误少 | 中性 | ✓（诊断闭环快） | 中性 | 中性 |
| 效率（工程） | 高 | 高 | 中（guard/deopt 维护） | 中 |
| 占用 | ~300-500KB 级（Janet 量级） | +Cranelift ~数 MB | 同左 | 运行时零增量 |

**结论（建议新决策 10）**：桌面/服务器默认 T1+T2（缓存命中后等效纯 AOT），WASM/移动纯 T1；T3 仅在长运行宿主（游戏主循环场景）按需启用；T4 独立工具链（`l-cli build`），不进宿主运行时依赖。占用维度上，Cranelift 的数 MB 是九维中唯一的实质代价——按用户向量（占用最末）可接受；若未来占用升优先级，MIR 是记录在案的轻量替换项。
