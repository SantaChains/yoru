## 1. 结论先行（五条）

1. **定位不变**：Yoru 不是「重写 Luau」也不是「Rhai 替代品」。长文第三章的风险清单（GC 暗坑/性能鸿沟/生态孤岛/多语言嵌入成本）与 20 号路线图的保守分期完全一致——Yoru 的差异化恰恰是 Rhai/Luau 都没有的：**typeck 一等公民 + AI 契约（签名即文档、诊断带 fix-it）+ 能力即参数**。长文的折中路线第 2 条（以现有引擎为基底外挂类型层）不采纳：Yoru 前端+typeck+LBC0 已完成，沉没的是正确投资。
2. **长文一处事实修正**：所谓 Luau「栈导向调用模型」不准确——Lua 5.0 起（含 Luau）字节码是**寄存器式**，长文真正的批评点应是 C 值模型与栈帧布局耦合。对 Yoru 的含义：LBC0 保持栈式（验证器简单、栈深可静态重算，阶段 2 已全绿）是正确取舍；寄存器式仅在 JIT 前夜才值得做，登记为远期演进项。
3. **debug 模式 = 编译期双产物 + VM 内建钩子**，不是运行时开关。借鉴 Odin（`ODIN_DEBUG` 是编译期常量）与 QuickJS（`JS_SetDumpFlags`），LBC0 的 FLAG_DEBUG 段（阶段 2 已预留）承载行号表 + 局部名表，strip 后即发布产物。
4. **LSP 有现成地基**：阶段 1 锁定的诊断 JSON schema v1 + yoru-syntax/yoru-typeck 公共 API 就是语言服务器的全部输入。emmylua_ls（Rust 实现的 Lua LSP）证明这条路在 Rust 侧完全可行；Godot 的教训是 LSP 依赖编辑器进程——Yoru 的 `yoru-lsp` 必须 headless 独立进程。
5. **一切以阶段 3 为落点**：本轮产出的不是新坑，是 T1 解释器的六条设计约束（§5）。

## 2. 各源事实摘要与可学点

### 2.1 Godot 4 GDScript（本轮调研确认的架构）

| 事实 | 出处 | 对 Yoru 的可学点 |
|---|---|---|
| 四段管线：Tokenizer → Parser/AST → **Analyzer**（类型+名字解析）→ Compiler → 字节码 VM（栈式，giant switch） | gdscript_parser/analyzer/compiler/vm.cpp | 与 Yoru 前端→typeck→LBC0 同构；管线划分被工业界再次验证 |
| **双路 dispatch**：`OPCODE_CALL`（运行时类型检查）vs `OPCODE_CALL_VALIDATED`（analyzer 证明类型安全时编译期选定） | gdscript_compiler.cpp / variant_call.cpp | typeck 已有的类型信息可以免费换快速路径——但属于 JIT 前优化，登记演进项，阶段 3 不做 |
| LSP **与 DAP 双协议内建**（端口 6005/6006），补全/定义跳转直接复用 analyzer | docs.godotengine.org | LSP 共享 analyzer 是正解；但 Godot LSP 依赖编辑器实例运行，是反面教材 |
| Variant 万能联合体贯穿全部层 | core/variant | 反面教材：Yoru 决策 6/13 已把值模型拆开，不回头 |

### 2.2 Odin（系统语言，只借思想不借形态）

| 事实 | 对 Yoru 的可学点 |
|---|---|
| `ODIN_DEBUG` 是编译期常量，代码可用 `when` 分支——debug 构建是**产物属性**而非运行时开关 | Yoru debug/strip 双产物决策（决策 70）的直接依据 |
| `assert` 失败自带 file/line；`trap`/`debug_trap` 二分；`core:debug/trace` 带 tracking_allocator（分配追踪+回溯） | 运行时信息（内存/分配）作为一等调试设施；Yoru 的 VM stats（决策 72）对标 JSMemoryUsage + tracking_allocator |
| `-vet` 族 lint 与编译器共用基础设施 | Yoru lint 已在 typeck（收窄/lint 组），不为 vet 另起炉灶 |
| context 系统（context.allocator 显式传上下文） | 印证 Yoru「能力即参数 Ctx」的取向；Odin 隐式 thread-local、Yoru 显式传参——AI 可读性上 Yoru 更优 |

### 2.3 QuickJS / QuickJS-ng（体量最接近 Yoru 目标形态的成熟 VM）

| 事实 | 对 Yoru 的可学点 |
|---|---|
| **中断计数器**：每 JSContext 一个 interrupt_counter，初值 10000，每基本块递减，归零才调 interrupt_handler；返回非 0 抛**不可捕获错误**终止 | 决策 71 的原型：资源三限的「指令预算」用计数器节流检查，不是每条指令查一遍——性能与可中断性的工业平衡点 |
| `JS_SetMemoryLimit`（硬顶）+ `JS_SetGCThreshold` + `JS_SetMaxStackSize` 三独立旋钮 | 对应 20 号资源三限（指令/内存/深度）——确认三旋钮独立、运行时可调是标准做法 |
| `JS_ComputeMemoryUsage` 返回 JSMemoryUsage 全量统计结构体 | 决策 72：`Vm::stats()` 返回快照结构体（指令数/堆/栈深/GC 计数），宿主轮询，不搞回调风暴 |
| JSRuntime（堆+GC）/JSContext（全局环境）两层分离，一 runtime 多 context | 对应 Yoru `Vm`（堆/资源）与 `Instance`（模块实例+Ctx）分层，04 号已有；QuickJS 验证了该切分够用 |
| `JS_Suspend/Resume` 状态快照、`on_progress` 式回调 | 协程/热重载是阶段 4+；快照式恢复登记演进项 |

### 2.4 Luau（2025 新类型求解器 GA 后的生态）

| 事实 | 对 Yoru 的含义 |
|---|---|
| 类型系统三模式 `--!nocheck/nonstrict/strict` 逐文件渐进 | Yoru 已是类型一等公民，无此包袱；但「逐文件渐进」验证了渐进类型在亿行级代码库的生存能力 |
| read/write 属性修饰符、user-defined type functions 是新求解器亮点 | 不跟进：Yoru 冻结表纪律（只减不增），类型函数属于类型层图灵完备，与「AI 审稿人可局部判定」冲突 |
| Lua LSP 生态碎片化：LuaLS 拒绝做调试器、EmmyLua 自研 Rust 分析器+独立调试器、lua-debug 稳定性欠佳 | 教训：**LSP 与 DAP 分 crate，但共享同一 analyzer**；不要让调试协议需求倒灌语言服务，也不要让两者各养一套前端 |

### 2.5 Rhai（长文第二篇 + 官方文档，只列差异点）

Rhai 的资源配额命名（max_operations/max_call_levels/max_string_size…）、on_progress 中断、Engine/AST/Scope 三件套解耦、默认封闭零后门——与 20 号设计高度同源，不再重复吸收。**不学**：动态类型（Yoru 有 typeck）、值传递 .clone() 语义（Yoru 值语义+RC 已定）、AST 序列化格式不承诺稳定（Yoru LBC0 有 CRC+版本位+验证器，是承诺稳定的发行格式，这是 Yoru 的相对优势而非弱点）。

## 5. 阶段 3（T1 解释器）设计约束清单

阶段 3 开工时以下为硬约束，全部来自本轮裁决：

1. 解释器主循环 = 栈式 + giant match（GDScript/QuickJS 同构已验证），热点优化不做（VALIDATED 双路留 JIT 前）。
2. `Vm`/`Instance` 两层分离（决策 69），堆按实例分区，无全局共享。
3. 资源三限独立旋钮 + 中断计数器节流（决策 71），死循环可被宿主线程打断。
4. debug 段（行号表/局部名表）在本阶段序列化与消费——运行时错误必须带源行回溯（决策 70）。
5. `stats()` 观测 API 与三限同批交付（决策 72）——可观测性与资源控制是同一套计数器的两个出口。
6. 差分测试目标：同输入下 debug 与 strip 产物行为一致（strip 仅删元数据，不改语义）。

## 6. 明确不做（负面清单）

- 不做 JIT / Wasm 后端（除非 Luau 级性能成为真实需求）。
- 不做 metatable 式元编程——能力显式化是沙箱与 AI 可判定性的根基。
- 不做绑定生成器/多语言宿主，直到出现第二个真实宿主。
- 不做 GDScript 式 @注解、Luau type functions、运算符自定义扩展。
- 不做回调式 profiler（stats 轮询够用）。
