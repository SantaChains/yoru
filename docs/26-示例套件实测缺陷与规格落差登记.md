## 1 缺陷登记表（D-01 … D-26）

### D-01 · Y-S9502 全文件累计 wrap 预算误伤合法文件 — Critical
- **复现**：同一文件放入约 57 条 `let x = a + b * 2 - 1` 形式简单语句，或约 50 条 fn 定义即触顶；120 行合法数学文件被拒，报错行号指向随机位置（非真实错误点）。
- **根因**：`crates/yoru-syntax/src/parser.rs:40` `MAX_CHAIN_LEN = 1000` 是**整个文件累计**计数；`wrap_guard`（:901-912）在每个优先级层循环（含退出迭代）都 +1，且计数器跨顶层声明**从不重置**（插值子解析器除外，:1496 `wraps: 0`）。成本模型：每裸表达式 ≈10 wraps，每二元运算符 +3，每索引/调用/字段 +1；16 元素 4×4 矩阵字面量 ≈210 wraps，三个即超预算。
- **workaround**：拆分多个精简文件（每篇 ≤ ~45 条密集表达式）；用构造器 fn 收字面量（调用点省预算）；避免 4×4 矩阵字面量。示例套件 `05` 因此由 mat4 重写为 Vec3 向量管线。
- **修复方向**：按顶层声明 / 语句边界重置 `wraps`；约束对象应为**单链长度**而非全文件累计。
- **已修（2026-10-13，showcase.yoru 红证复核）**：登记的「阈值/根因数据存疑」结论被推翻——`examples/showcase.yoru` 前 115 行（≈60 条普通语句）即耗尽 1000 预算，head-115 通过 / head-116 触顶，复现稳定。真根因比原登记更精确：**六站（or/and/shift/chain/chain_multi/postfix）的 `wrap_guard()` 前置于运算符匹配**——即使下一 token 非运算符（试探失败）也扣 1，每个表达式按优先级层数（≈7 层）白扣。根修：guard 后置到运算符命中之后（**试探零成本，预算语义 = 单文件实际链长 ≤1000**，50k 拒绝测试语义保持）。回归 +1（`wrap_budget_counts_links_not_probes`：300 条 × 2 实际链 + 后缀试探不再触顶）。

### D-02 · 插值 `${x!}` 以 `!` 结尾 → Y-S9502 无限自旋 — High
- **复现**：`let s = "${o!}"`（o 为 `T?`）→ Y-S9502。
- **根因**：插值子解析器（`parser.rs:1483` `parse_str_parts`，:1496 建子解析器 `wraps: 0`）的 token 切片**无 Eof 哨兵**；`parse_postfix`（:1216）循环仅靠 `at_eof()` 终止，而子解析器 token 无 Eof → `peek()` 越界钳制回最后 token（`parser.rs:65` `tokens[pos.min(len-1)]`）、`bump()` 拒绝越过 `len-1`（:83-85）→ 循环永不前进，直到 `wrap_guard` 触顶。
- **workaround**：`"${(o!)}"`（括号包住解包，子解析器以 `)` 干净收尾）或先 `let v = o!` 再 `"${v}"`；`"${o! + 1}"` 因尾部 Int 偶发可过（Plus 退出 postfix）。
- **修复方向**：插值子解析器 token 末尾追加 Eof；`parse_postfix` 加 `at_eof` 守卫。

### D-03 · struct 运算符重载 typeck 放行但 VM 崩 — Critical
- **复现**：
  ```yoru
  struct Vec3 { x: float, y: float, z: float }
  impl Add for Vec3 { fn add(a: Vec3, b: Vec3) -> Vec3 { Vec3 { x: a.x + b.x, .. } } }
  fn f() -> int { let c = a + b; return 0 }   // typeck 过，运行 Y-R9007
  ```
- **根因**：`check_arith`（`yoru-typeck/src/check.rs`）查 `impls` 协议表放行，但 `lower` 发裸 `Opcode::Add`；VM 对 struct 操作数报 `Y-R9007`。`impl` 方法亦不可作自由函数调用（`Y-T0001`）。
- **workaround**：全部改自由函数 `fn add3(a: Vec3, b: Vec3) -> Vec3`。示例套件 01/02/05 全部采用自由函数。
- **修复方向**：`lower` 阶段对 struct 操作数改发协议方法调用；或 typeck 拒绝未实现协议的 struct 算术（ fail-fast 优于运行期崩溃）。**已修（2026-10-13，30 号定夺 fail-fast）**：`check_arith` 对 Named 同型算术**一律编译期拒绝**（Y-T0022）——已 impl 也拒（诊断明示「协议算术执行管线尚未实现，随泛型批次接入」+ 改自由函数建议），未 impl 保持决策 21 原语义；lower 发协议调用的预测性半分发器方案被否（泛型批次落地时必返工）。回归 +1（两情形断言），examples 11/11 不受影响（本用自由函数），全仓 164 测试全绿。

### D-04 · 收窄分支内 `x!` 被 Y-T0004 误拦 — Medium
- **复现**：
  ```yoru
  fn f(o: int?) -> int {
      if o != nil {
          let v = o!        // Y-T0004：期望先做 nil 检查（诊断自相矛盾）
          return v + 1
      }
      return 0
  }
  ```
- **根因**：`narrow_facts` 已将 `o` 静态窄化为 `int`，但 `!` 解包算子在该上下文仍被误判为「未做 nil 检查」。
- **workaround**：分支内直接用名（已窄化，无需 `!`）：`let v = o`。
- **修复方向**：放宽 `!` 在已收窄上下文的接受（值已是 `T`，不应再要求 nil 检查）。

### D-05 · 收窄值运行期仍是 Variant（静默类型/运行期错位）— High
- **复现**：
  ```yoru
  fn f(o: int?) -> int {
      if o != nil {
          let r = o + 1.0   // o 已窄化，运行期仍是 Variant → Y-R9007 <variant 1>2.5
          return 0
      }
      return 0
  }
  ```
- **根因**：nil 收窄是**纯静态层**；运行期值仍是 `Variant(Some(...))`，VM 算术对 `Variant` 操作数报 `Y-R9007`，插值显示 `<variant 1>2.5`。
- **workaround**：在**分支外** `let v = o!` 解包后再用（实证可得正确值）；避免在收窄分支内直接做运算。
- **修复方向**：收窄后真正运行期 unwrap，或 VM 算术接受 `Variant` 透传。

### D-06 · struct 字段简单赋值静默 no-op — Critical
- **复现**：`p.x = 9.0` 后 `print(p.x)` 仍输出 `1.0`（期望 9.0）。
- **根因**：`lower.rs:1487-1492` 简单 Field 赋值路径：`lower_lvalue_prefix(base)` 把容器压栈 → `lower_expr(value)` 压值 → `SetField` 弹 (值,容器) 压容器 → `Pop`（:1491）**丢弃栈上容器副本**，未回写 `base` 局部槽位。
- **workaround**：函数式更新 `Vec2 { ..p, x: 9.0 }`。示例套件 02/03 采用此 idiom。
- **修复方向**：Field 赋值走槽位回写（同 `SetIndexLocal` 快路径机制，决策 80）。

### D-07 · struct 字段复合赋值崩溃 Y-R9012 — Critical
- **复现**：`p.y += 1.0` → `Y-R9012 cannot set field y on 3.0`（操作数顺序颠倒，把值当容器）。
- **根因**：`lower.rs:1493-1503` 复合 Field 路径对 `SetField` 的 (容器, 值) 操作数序列错位（`GetField` 读出的字段值被当作容器传入 `SetField`）。
- **workaround**：函数式更新 `Vec2 { ..p, y: p.y + 1.0 }`。
- **修复方向**：修正复合 Field 路径 `GetField`/`SetField` 操作数顺序。

### D-08 · 复合索引赋值崩溃 Y-R9013 — Critical
- **复现**：`xs[1] += 5` → `Y-R9013 cannot index 1 with [9,2,3]`（操作数互换）。
- **根因**：`lower.rs:1532-1546` 复合 Index 路径：栈在 `lower_lvalue_prefix(base)` + `lower_expr(idx)` 后为 `[container, index]`；但 `StoreLocal` 弹栈顶，`tc`（:1534）存进**索引**、`ti`（:1536）存进**容器**——两临时变量顺序互换 → 后续 `GetIndex`/`SetIndex`（:1539/:1544）收到 (index, container) 而非 (container, index)。
- **workaround**：先读后写 `xs[1] = xs[1] + 5`（走 `SetIndexLocal` 快路径，:1518）；或避免复合索引赋值。
- **修复方向**：交换 :1534 与 :1536 的 `StoreLocal` 目标（或调整前缀/索引压栈顺序）。

### D-09 · 链式索引赋值静默 no-op — Critical
- **复现**：`c[0][1] = "#"` → 输出 `....`（期望 `.#..`）。
- **根因**：与 D-06 同族——`lower.rs:1527-1530` 简单 Index 赋值路径对内层 `SetIndex` 操作**栈上副本**，外层 `Pop`（:1530）丢弃，未沿链回写根局部 `c` 的对应单元格。
- **workaround**：扁平化结构或函数式重建整行/整表；示例套件 06 因此改用纯函数距离场（无可变 canvas 单元格写入）。
- **修复方向**：链式 Index 赋值回写根槽位（多层 `SetIndexLocal` 透传）。

### D-10 · for-kv map 迭代被拒 — High
- **复现**：`for k, v in m { ... }` → `Y-T0002 Map 迭代在阶段 2 提供 keys/values 通道`。
- **根因**：VM `resolve_iterable` 仅支持 List/Range（spec 19.4/19.6 却承诺 KV 迭代）。
- **workaround**：`for k in keys(m) { let v = m[k] }`。示例套件 11 采用 `for k in keys(m)`。
- **修复方向**：实现 for-kv，或 spec 明确删除该承诺（与 §19.9 落差对齐）。

### D-11 · `|> 裸名` 管道 rhs 被拒 — Medium
- **复现**：`dirs |> sort` → `Y-T0021`（rhs 必须为调用）。
- **workaround**：`dirs |> sort_floats(...)` 或 `dirs |> (fn(xs) = sort(xs))`。示例套件 01 用 `dirs |> map(fn(v) = length(v)) |> sort_floats`（rhs 恒为调用）。
- **修复方向**：允许管道 rhs 为裸名（解析为对该名的调用）。

### D-12 · distinct 构造 `UserId(42)` 被拒 — Medium
- **复现**：`let u = UserId(42)` → `Y-T0001 未知类型 UserId`（distinct 名被当 tag/变体构造）。
- **workaround**：`let u = 42 as UserId`（distinct ↔ 基类型往返，决策 26 唯一通道）。示例套件 11 采用 `42 as UserId`。
- **修复方向**：允许 distinct 构造语法，或文档明确仅 `as` 通道。

### D-13 · 泛型函数 `fn f[T]` 被拒 — Medium
- **复现**：`fn first[T](xs: [T]) -> T { ... }` → `Y-T0001 未知类型 T`。
- **根因**：typeck 未实例化泛型函数参数。
- **workaround**：用具体类型函数或 `any`/变参替代。
- **修复方向**：泛型函数实例化（与 D-14/D-15 同属泛型落地批次）。

### D-14 · 泛型 tag 变体构造断裂 — Medium
- **复现**：`Node(Node2<int> { x: 1, y: 2 })` → payload 解析无类型替换，且 `check_call`（`yoru-typeck/src/check.rs` ~2113）返回 `Ty::named(owner, vec![])` **丢弃类型实参**。
- **根因**：变体构造的 payload 类型参数未传播。
- **workaround**：避免泛型变体嵌套构造。
- **修复方向**：变体构造传播类型实参到 payload 类型。

### D-15 · 方括号泛型字面量 parse 错 — Medium
- **复现**：`Node2[int] { }` → parse 错误（parser 仅识别 `Ident <...> {`）。
- **workaround**：用尖括号 `Node2<int> { }`（可解析为 struct lit，但见 D-14 变体构造仍断）。
- **修复方向**：方括号泛型字面量解析（与尖括号等价）。

### D-16 · try 须 Result 上下文，诊断费解 — Medium
- **复现**：`pub fn main() -> int { let v = try f() }` → `Y-T0019`（信息未说明「try 仅在 Result 返回函数内」）。
- **workaround**：try 收在 `-> Result[...]` 返回的函数内；`main` 返回 `Result[...]` 亦可（示例套件 11 `result_demo`）。
- **修复方向**：诊断信息明确约束来源。

### D-17 · if 表达式作为值全面静默 nil — Critical（高危）
- **复现**：
  ```yoru
  fn f(x: int) -> int {
      let y = if x > 1 { 1 } else { 0 }   // y 运行期为 nil（静默！）
      return y
  }
  // 多行 / lambda 体 / int 分支 全部同灭：print("${y}") → nil
  ```
- **根因**：if 的 lower 路径**未把分支选中值压栈**；spec 19.81/87 明确 `if_expr` 为 primary 且「作值必带 else」，实现缺口。
- **影响**：静默返回 nil 而非期望值，属最危险一类（无报错、结果错）。
- **workaround**：if **语句** + 早返回（示例套件 04 `sin` 约减、07/08 全部采用）。
- **修复方向**：if 表达式 lower 为「分支结果压栈」，与 match 表达式（D-18 之外已可用）对齐。

### D-18 · match 不能直接匹配 Result — High
- **复现**：`match r { Ok(n) => ..., Err(e) => ... }` → `变体模式要求 tag 类型`（spec 19.226 示例本身错误）。
- **workaround**：`let v = r!` / `r == nil` / `try` 传播（示例套件 11 用 `try` 链）。
- **修复方向**：允许 Result 作为 match 目标，或修正 spec 19.226 示例。

### D-19 · `parse_int` 模块归属与 spec 不符 — High（spec 落差）
- **复现**：`j.parse_int("42")`（spec 19 写法）→ 未定义；实际为裸内建 `parse_int("42")`。
- **根因**：stdlib 注册表（`yoru-stdlib/src/lib.rs`）中 `parse_int/parse_float` 是裸 BUILTINS，不在 `json` 模块下；`json.parse/stringify` 才在 `json` 模块。
- **workaround**：裸 `parse_int(s)` / `parse_float(s)`；`json` 模块仅 `parse`/`stringify`。
- **修复方向**：统一模块归属，或修正 spec 19 示例。

### D-20 · 窄化后 Ok 的 Result 运行期泄漏 Variant — Critical
- **复现**：
  ```yoru
  fn half(s: string) -> Result[int, Err] {
      let n = parse_int(s)        // n: int?（未解包）
      if n == nil { throw BadInput(s) }
      return Ok(n)                // n 静态已窄化为 int
  }
  // 调用点 print 显示 <variant 1>21（运行期仍是 Variant）
  ```
- **根因**：throw/narrow 路径下，窄化后的 `int` 运行期表示未消除 `Variant` 包装。
- **workaround**：调用点 `parse_int(s)!` 解包（静态仍是 `T?`，但运行期值正确）。
- **修复方向**：统一窄化运行期表示（与 D-05 同源）。

### D-21 · throw 运行期中止且变体名丢失 — High
- **复现**：`throw NotFound` → 进程中止，信息 `raised: <variant 0>`（变体名 `NotFound` 未保留）。
- **根因**：throw 运行期 raised 路径未格式化变体名/载荷。
- **workaround**：不在示例热路径演示 throw（示例套件 11 仅注释提及）；用 `Result` + `try` 传播替代可见 throw。
- **修复方向**：raised 信息保留变体名与载荷（诊断五要素，见 20 号）。

### D-22 · 字符串 `+` 拼接自相矛盾 + `stringify` 返回 Json — High
- **复现**：`let s = "a" + "b"` → typeck `期望 string，得到 string`（自相矛盾）；`stringify(42)` 返回 `Json` 而非 `string`。
- **根因**：`+` 对 string 操作数的 typeck 分支逻辑错误；`stringify` 内建返回类型登记为 `Json`（实际应 `string`）。
- **workaround**：用 `print` 多参或插值拼接；`stringify` 结果不可直接参与字符串运算。
- **修复方向**：`+` 支持 string 拼接；`stringify` 返回 `string`（或文档说明）。

### D-23 · 列表 spread `[..a, ..b]` parse 失败 — Medium
- **复现**：`let c = [..a, ..b]` → parse 错误（仅 struct spread `Vec2 { ..p, x: 1 }` 被支持）。
- **根因**：`lower`/parser 仅实现 struct spread，未实现 list/array spread。
- **workaround**：`for` 累积或 `map`/`filter` 组合；示例套件 03 用 struct spread，未用 list spread。
- **修复方向**：列表/数组 spread 解析（spec 19 暗示集合 spread）。

### D-24 · 嵌套 lambda 传递捕获崩溃 Y-I9004 — Critical
- **复现**：
  ```yoru
  fn f() -> int {
      for r in range(0, 3) {
          let row = map(range(0, 3), fn(x: int) =
              map(range(0, 2), fn(y: int) = y + r))   // 内层 lambda 捕获祖父 r → Y-I9004
          print("${row[0][0]}")
      }
      return 0
  }
  ```
- **根因**：中间层 lambda 未把祖父作用域变量 `r` 向上传播为自己的 upvalue；VM 闭包捕获 `yoru-vm/src/lib.rs:594`（及 :624/:638）暴露 `Y-I9004 upvalue index out of range`。自由变量分析不穿透嵌套 lambda。
  - 精确条件：内层 lambda 捕获**非直接父级**的变量（须跳过一层）即崩，除非中间层也引用该变量使其被传播（实测 `map→map` 捕 `x`+`r` 崩、`map→fold` 只捕直接父级 `x` 正常）。
- **workaround**：把内层生产收进顶层 fn（fold/map lambda 只捕直接父级局部，走 is_local 快路径）。示例套件 06 `any_near(segs, px, py)` 即此手法。
- **修复方向**：嵌套 lambda 自由变量向上穿透传播（中间层自动成为传递 upvalue）。**已修（2026-10-13）**：根因不在 resolve_capture 递归链（其语义本自洽），而在 `lower_lambda` 以 **clone** 继承捕获层——内层 lambda 对中间层 upvals 的传递条目登记进克隆体，lambda 结束恢复 outer 时全部丢失（中间层 `proto.upvalues` 落空 → VM 取值越界）。根修：captures 改 **move** 语义（`mem::take` + 尾部放回含新条目的中间层）。回归 +2（祖父捕获 / for 变量逐轮快照），examples 11/11，全仓 160 测试全绿。

### D-25 · `rune` 不可转 `int` / 无 codepoint 内建 — Medium
- **复现**：`let cp = r as int`（`r: rune`）→ `Y-T0011 非法转换：rune as int`（决策 26 限定 `as` 仅数值互转与 distinct 往返）；遍历 rune 无法取码点。
- **根因**：rune 为不透明类型，无 `codepoint(rune) -> int` 内建。
- **workaround**：迭代 rune 做计数/索引，不取码点（示例套件 11 改为 rune 计数）。
- **修复方向**：提供 `codepoint(rune) -> int`，或允许 `rune as int`。

### D-26 · W-T0002 未用变量警告 — Low（Lint）

### D-27 · typeck 拒绝一切 Result-match（Ok/Err 模式 Y-T0002）— Critical（showcase 红证）
- **复现**：`match find(...) { Ok(v) -> ... Err(e) -> ... }`（scrutinee `Result[int, E]`）在 typeck 全数报「变体模式要求 tag 类型，得到 `Result[int, E]`」；同形源码 VM 测试（`match_and_try_propagation`）通过——**VM 测试的 `compile()` 不含 typeck**（parse→lower→verify），落差被测试架构掩盖。
- **根因**：`check_pattern` 的 `Pattern::Variant` 臂只接受 `Ty::Named` scrutinee，而 `Result` 是独立 `Ty::Res(ok, err)` 构造——运行时（lower `variants` 注册 `Ok`/`Err` 内建变体）早已支持，typeck 缺位。连带级联：臂绑定名 Y-T0001 未定义、臂型退化 unit、Y-T0015 误报未穷尽。
- **语义注记**（修时对齐 lower 实证）：payload 是**绑定名**（`Err(e)` 绑 `e: E`；`Err(NotFound)` 绑名为 NotFound 的局部，非嵌套变体检查）；Result 构造器 `Ok(...)`/`Err(...)` 的类型上下文**仅来自 return 位**（Y-T0018 help 明示），let 初始化位的臂构造器退化为 unit——Result-match 实际只能作 return 表达式使用（spec 19 §226 示例形态）。
- **已修（2026-10-13）**：`check_pattern` 增 `Ty::Res` 的 Ok/Err 模式臂（payload 按绑定名，与 lower 语义一致）；`check_match` 穷尽性增 `Ty::Res`（Ok+Err 齐备即穷尽）。回归 +1（`result_match_patterns_typeck`：正形 + 缺 Err 臂 Y-T0015）。
- **复现**：声明未使用的局部绑定 → `W-T0002 变量未使用`（决策 40-43 的卫生警告）。
- **根因**：Lint 层未用符号检测（良性）。
- **workaround**：用 `let _ = x` 显式丢弃（示例套件 11 `let _ = result_demo()`）。
- **修复方向**：无（属预期 Lint）；可细化未用检测精度。

## 5 nil 设计自我剖析：会不会导致程序不安全

> 2026-10-12 追加。用户命题「思考 nil 会不会导致程序不安全，读文档怎么设计引入的，自我剖析」。结论：**内存/UB 层面 nil 不导致不安全（它是标签值非指针）；逻辑层因实现未履约重新引入「十亿美元错误」**。

### 5.1 文档怎么把 nil 设计进来（溯源）
- **03-类型系统 §3.1.3**（最高原则）：「空安全：**无 null**；缺省值用 `Option<T>`。`Option` 与 `T` 之间无隐式转换。」——nil 是 `Option<T>` 的 `None` 值，不是独立空指针类型。
- **决策 27**（11-决策记录）：`T → T?` 隐式加宽（零信息丢失，Swift 先验）；`T? → T` **永不隐式**，仅 `!`。单向加宽保住 nil 检查有效性。
- **决策 39**：禁嵌套 `T??`（canonical form），语法层堵死 null 套娃。
- **决策 40**：流敏感智能收窄——`if x != nil` 分支内 `x` 自动为 `T`；`!` **降级为逃生舱**；预判别名陷阱「重新赋值即失效；闭包按值快照保证无别名失效」（19 §139）。
- **决策 54**：`try` 双传播（Result→Err、`T?`→nil）。
- **04-执行引擎 §26**（关键规划）：「Option/Result：**IsNone/Unwrap（编译器在非空路径生成**；擦除策略下 Option 展开为 tagged 值）」——设计**明确要求 lower 在收窄路径插 `Unwrap` 剥 Option 标签**。
- **19-语法规范v2 §191-205** 旗舰范式：`let mut best: Item? = nil` … `if best != nil { let b = best // 分支内 b: Item }`，承诺之后可当 `Item` 用。

### 5.2 实现侧表示（证据）
- nil 两种表示：`Value::Nil`（裸值，`crates/yoru-vm/src/builtins.rs:344`）与 `Value::Variant(variant:0, payload:None)`（Option None，:337-340）。均**带标签、非指针**。
- `Map 缺键取 nil`（决策 55，`yoru-vm/src/lib.rs:13`）；`GETFIELD fail-open 归宿主`（`demo.rs:25`）——有意 fail-soft，类型系统之外开静默 nil 注入口。

### 5.3 自我剖析结论
| 维度 | 结论 | 依据 |
|---|---|---|
| 内存/UB | **安全** | nil 是标签值非指针；值语义 + `Rc` + 溢出抛错（决策 29/16）兜底，无空解引用/UAF |
| 类型层空安全 | **设计健全** | 决策 27/39/40/54 + 03 §3.1.3 = Swift/Kotlin/Flow 模型 |
| 运行期空安全 | **被破坏** | 收窄不剥标签（`<variant 1>2.5`，D-20/t42）、`if` 表达式静默 nil（D-17）、`!` 收窄分支误拦（Y-T0004）——三类叠加＝「类型说安全、运行期仍 nil 形状」 |
| 设计取舍风险 | **决策 55 fail-soft 需复核** | 缺键静默返回 nil，拼写错键不报错直接流成 `V?` 形状 |

- **关键反证**：19 §191-205 的旗舰收窄范式，今天运行期会崩——你做了 nil 检查，值却仍是 `Variant` 包装（04 §26 规划的「非空路径插 `Unwrap`」在 stage-2 未落地；12-实现工作台 §13 诚实声明「变体构造不带类型标签」延至 stage 3）。
- **设计自身取舍（非缺陷）**：`!` 恐慌逃生舱＝明示契约（错就 panic，同 Swift）；`try` 双传播掩盖「哪种失败」，是 ergonomics 取舍非 unsafety。
- **表示脆弱点**：nil 双表示（`Value::Nil` vs `Value::Variant(None)`），`== nil` 必须两边认，路径相关漏判＝实现债。

### 5.4 修复方向（全在 stage 3，不动语法）
1. lower 在流敏感收窄路径插 `Unwrap`（兑现 04 §26），剥掉运行期 Option 标签——根治 D-20 类 `<variant N>` 崩溃。
2. `if` 表达式产值（兑现 19 §81/87 `if_expr`），根治 D-17 静默 nil。
3. `!` 在已收窄分支豁免（与决策 40「收窄后不需要 `!`」自洽）。
4. 决策 55 改为可配置 fail-fast（缺键默认抛错，fail-soft 走显式 `get` 通道），堵静默 nil 注入口。
5. 统一 nil 单表示（消除 `Value::Nil` / `Value::Variant(None)` 双轨），`== nil` 单路径判定。
