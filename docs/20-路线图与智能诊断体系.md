## 2. 错误模型：每种错误的情况、原因、修复方向

用户要求「语言错误的情况和原因要清晰明确」——Yoru 的答案是把错误做成**一等数据**：每条诊断 = 错误码 + 五要素（§2.2），每类错误在文档站有长文 explanation（借鉴 rustc `rustc_error_codes` 的 EXXXX.md 模式）。

### 2.1 错误分类学（五域）

| 域 | 前缀 | 何时产生 | 是否可自动修复 | 典型代表 |
|---|---|---|---|---|
| 词法/语法 | `Y-S0xxx` | parser/lexer | 高（括号补全/分隔符/拼写建议） | 非法记号、缺 `}`、换行处表达式断裂 |
| 类型 | `Y-T0xxx` | typeck | 高（as 补全/收窄利用/协议方法缺失清单） | int×float 混算（决策 26）、nil 解引用风险、协议未实现 |
| 运行时 | `Y-R0xxx` | VM 执行 | 部分（定位精确到帧；建议修复源码） | 溢出抛错（决策 29）、除零、越界、nil 强解包 `!` 失败、栈深上限 |
| 宿主 | `Y-H0xxx` | 宿主桥/能力调用 | 宿主定义 | 能力未授权、牢笼逃逸拒绝、SSRF 守卫拦截、凭据缺失 |
| 内部 | `Y-I0xxx` | 编译器/VM 自身 bug | 永不（这是 bug 不是用户错误） | ICE：VM panic、验证器拒绝合法字节码 |

**关键纪律**：`Y-I`（内部错误）与用户错误的界限是硬的——**任何 `Y-I` 都视为 Yoru 自身的缺陷上报**（决策 60），绝不包装成用户错误输出。这与 Rhai「任何 panic 都是 bug」契约、wasmtime 的 ICE 处理同源。

### 2.2 诊断五要素（每条诊断必须齐全）

借鉴 rustc JSON 诊断结构（`--error-format=json`）与 clippy 的 suggestion 体系：

1. **code**：错误码（如 `Y-T0308`）+ 文档站长文链接；
2. **spans**：主 span（primary）+ 次要 span（相关位置，如「协议在此定义」「类型在此推断出」）——多 span 是「原因清晰」的关键：**错误发生在哪 + 为什么会这样**两个位置都要给；
3. **message**：一句话主消息，脱离上下文可读；
4. **children**：原因链（note/help 子诊断）——类型错误的「期望 vs 实际」（expected/actual type diff）必须显式给出，Elm 实证这是错误消息质量的分水岭；
5. **suggestions**：结构化修复建议，带 **Applicability 四级**（rustc 同款）：

| 级别 | 语义 | 处置 |
|---|---|---|
| `MachineApplicable` | 可安全自动应用 | §3.3 修复闭环可直接应用（仍需重编译验证） |
| `MaybeIncorrect` | 方向对但需人/AI 判断 | 仅建议，不自动应用 |
| `HasPlaceholders` | 需要补内容（如缺失的标识符名） | 仅建议 |
| `Unspecified` | 只有提示价值 | 仅建议 |

**JSON schema 与人类渲染同源**：一套诊断结构两个 emitter（16.4 T4 已定）。机器侧字段顺序、字段向前兼容规则照抄 rustc JSON 文档纪律（新字段可加、枚举可扩、消费方必须容忍未知字段）。

### 2.3 高频错误速查表（实现 §2 阶段前冻结，作为 ui-test 的种子清单）

| 错误码 | 情况 | 原因 | 修复方向（suggestion 级别） |
|---|---|---|---|
| Y-S0001 | 意外的换行 | 上一行以非延续记号结束（19.1 延续规则） | 提示行尾补运算符或合并行（MachineApplicable） |
| Y-S0002 | 缺 `}` | 块未闭合，给出**块的起始行** | 补全（MachineApplicable） |
| Y-S0003 | 非法记号 | 源码含 Bidi/零宽字符或非法 ASCII 外标识符 | 指出码点（Trojan Source 守卫，决策 51），永不静默剥离 |
| Y-T0308 | 类型不匹配 | expected/actual diff | 若仅数值宽度差 → 建议 `as`（MachineApplicable）；否则展示两类型结构 |
| Y-T0309 | int/float 混算 | 决策 26：数值类型不隐式互换 | `x as float` 补全（MachineApplicable） |
| Y-T0310 | 对 `T?` 直接使用 | Option 未解包，智能收窄（决策 40）不适用此位 | 建议 `match`/`try`/`!= nil` 收窄（MaybeIncorrect——三种收窄语义不同） |
| Y-T0311 | 协议方法未实现 | impl 缺方法 | 列出全部缺失签名（HasPlaceholders） |
| Y-T0312 | distinct 类型互换 | 决策 23：新命名类型不隐式互换 | 显式 `as`（MachineApplicable） |
| Y-T0313 | 忽略 Result | 决策 34 | `let _ =`（MachineApplicable）或 `try` 传播（MaybeIncorrect） |
| Y-R0101 | 算术溢出 | 决策 29：算错了就响 | 帧栈 JSON 指出溢出表达式；环绕需求提示 `+%`（P2 实现） |
| Y-R0102 | 除零/取模零 | 决策 44 | 帧栈定位；提示前置除数检查（MaybeIncorrect） |
| Y-R0103 | `!` 解包 nil | 决策 54：`T?` 为 nil 时 `!` 抛错 | 帧栈定位 + 建议收窄代替强解包 |
| Y-R0104 | 资源超限 | 内存/指令/栈深三限之一 | 结构化指明哪一限、当前值、上限（§5.1） |
| Y-H0201 | 能力未授权 | 调用了签名未注入的能力（能力即参数的编译期面）→ **理想情况下在 typeck 就拦**，VM 层是纵深防御 | 指明缺失能力与宿主授权方式 |
| Y-I0001 | 内部编译器错误 | Yoru 自身缺陷 | 恐慌消息 + 最小复现引导 + 上报通道（决策 60） |

### 2.4 「原因清晰」的三条硬规则

1. **每个错误码必须有 explanation 长文**：什么时候发生、为什么语言这样设计、三种以上修复路径对比——文档站生成自诊断定义处（单事实来源）。
2. **类型错误必须带 expected/actual**：省略即实现 bug（ui-test 快照强制）。
3. **错误不得级联轰炸**：同一根因只报一条主诊断（rustc 的 parent/children 模式），parser 错误恢复保证单文件多错误各自独立定位，不互相污染。

## 3. 智能诊断：三级智能 + 修复闭环

### 3.1 设计立场

「软件智能一点，检测实现可能的错误并自动 fix」在 Yoru 里落地为**三级智能金字塔**，每级有明确的能力边界与置信度纪律（不假装聪明、不静默改码）：

```
L3 修复闭环（AI 时代差异化能力）
   └ L2 Lint 体系（统计性可疑模式检测）
      └ L1 确定性 fix-it（编译器内建，零误报底线）
```

### 3.2 L2：Lint 体系（clippy 分类学整体移植）

clippy 的九组分类经十年审计验证，直接移植为 Yoru lint 分组，**分组即默认级别即置信度承诺**：

| 组 | 默认级别 | 承诺 | Yoru 例子 |
|---|---|---|---|
| correctness | **deny** | 零误报才准入（clippy 纪律） | `==` 比较不同 distinct 类型（typeck 已拦，lint 兜底） |
| suspicious | warn | 大概率写错但可能是故意 | 对 `T?` 用 `== nil` 后又用 `!`（应改收窄） |
| style | warn | 惯用法 | 插值替代 `+` 拼串（决策 14.6 的 lint 化） |
| complexity | warn | 简事复杂写 | 可合并的嵌套 if |
| perf | warn | 性能坑 | 热循环内建大 map 字面量（应提为顶层 const） |
| pedantic | allow | 严格但有误报 | 全部命名约定类 |
| nursery | allow | 新 lint 孵化（clippy 证明孵化通道必要） | — |
| restriction | allow | 禁用某特性（按需启用，永不整组开） | 禁 `!` 强解包（高安全宿主场景） |

**lint 稳定性契约**（照抄 clippy 1.0 RFC）：lint 只增不删、可重分类、可废弃（废弃=空转保名）；修 false positive 属正常演进，false negative 修复不得超出 lint 名称的文档范围。

### 3.3 L3：修复闭环（AI 原生诊断的兑现）

学术与大厂证据：
- **Ericsson 工业 CI 实证**（arXiv 2510.13575，4 万+ 提交）：LLM 驱动的编译错误自动修复，综合 prompt（错误日志 + 出错片段 + 历史人工修复样例）下 **63% 修复率，其中 83% 被工程师评为合理**，64% 成功案例 8 分钟内完成——对照人工通常数小时。
- **Meta SapFix/Getafix**：AST 层修复 + 历史修复模式挖掘，已入生产。
- **APR 2025 共识**：故障定位 → LLM 补丁生成 → **测试验证** → 补丁排序；瓶颈在定位精度与过拟合（test-suite overfitting）。

Yoru 的结构性优势是**把 APR 的三个瓶颈直接做进语言**：
1. **定位精度**：签名即完整契约 + 多 span 原因链 → 诊断 JSON 本身就是高精度故障定位，不需要 spectrum-based 定位；
2. **补丁约束**：规范形式（一操作一形式）→ 合法补丁空间极小，LLM 自由度被文法钳制（Anka 路线的诊断侧收益）；
3. **验证 oracle**：**VM 快照分叉**（14 号差异化设计）让补丁验证无需测试用例——补丁在分叉 VM 里对固定输入试运行，与原程序对比行为差异，**这是 Ericsson 论文「编译错误无测试可验证」痛点的语言级解法**。

闭环协议（`yoru fix` CLI，阶段 5 交付）：

```
诊断 JSON（含 MachineApplicable suggestion）
  → L1 级：直接应用 suggestion → 重编译 → 通过即输出 diff
  → L2 级：lint suggestion 排序后逐个尝试（每次重编译验证）
  → L3 级：诊断 JSON + 词汇表存根（.yorui）+ 权威样例喂给外部 LLM
       → 返回 patch → 分叉 VM 试运行验证 → 通过才采纳
```

**安全闸门（决策 59）**：只有 `MachineApplicable` 且重编译通过的建议可自动应用；L3 patch 永远以 diff 形式输出待确认，除非宿主显式开启 auto-apply。**自动修复不允许静默改变程序语义**——修复必须是「使代码符合程序员/规范形式的明显意图」。

### 3.4 智能检测的可扩展面

- **统计可疑度**（P2）：基于权威语料的「低自然度检测」——偏离规范形式审计表的写法视为可疑（这是 clippy style/perf 的数据驱动升级）；
- **差分自检**（P2，wasmtime fuzzbull 启发）：用户代码在「VM」与「参考树遍历解释器」双引擎下结果不一致 = 编译器 bug，固化为一等自检工具 `yoru differential`；
- **AI 审稿面**（P2）：语义可局部判定（15 号 AI 三重身份铁律 3）使 lint 可以做「局部签名不一致」类检测而无需全程序分析。

## 4. 测试与安全检测体系

[10-抗冲击测试体系](10-抗冲击测试体系.md) 的 SQLite 精神保持权威，本文档把它落到 Yoru 的具体测试资产与工具：

### 4.1 测试金字塔（自下而上）

| 层 | 资产 | 工具/形式 | 门槛 |
|---|---|---|---|
| 单元 | 每 crate | `cargo test` | 零警告（`[lints] workspace = true` 已落地）；新诊断必须有配对测试 |
| ui-snapshot | 诊断输出精确快照 | rustc tidy 模式：`.yoru` 输入 + `.stdout` 期望文件 | 诊断文本变更必须显式 bless（防静默退化） |
| doctest | `///` 文档示例可执行 | 阶段 5 | stdlib 100% 公共 API 覆盖 |
| 属性 | 决策不变量（如 floor-mod 非负、Map 插入序、收窄 sound） | QuickCheck 式（16.4 T5） | 每条语义决策至少一条性质测试 |
| 差分 | 双引擎一致性 | §4.3 | 见门槛 |
| fuzz | §4.2 四目标 | libFuzzer/cargo-fuzz | 见门槛 |

### 4.2 Fuzz 四目标（wasmtime 投影）

wasmtime 的实践（OSS-Fuzz 24/7、fuzz 门槛=提案进 Tier 1 的必要条件）是 VM 稳定性的工业金标准，投影为四目标：

1. **yoru-syntax-fuzz**：任意字节 → lexer/parser。oracle：不 panic、不死循环（阶段 0 已实修过 Eof 死循环——正是这类 fuzz 要拦的 bug 类）、诊断 span 不越界；
2. **yoru-gen-fuzz**：wasm-smith 式**结构化程序生成器**（按 EBNF 生成合法+半合法程序，带生成器级 trap 回避）→ typeck/编译器 oracle：编译器自身不 panic（ICE=Yoru bug）、诊断与生成器注入的已知错误一致；
3. **yoru-differential**：生成程序在 **VM vs 参考树遍历解释器** 双引擎执行，比较输出（NaN 位型 canonicalize 后比较——wasmtime 实证经验）。这是优化器/VM 正确性的主 oracle；
4. **yoru-resource-fuzz**：生成资源密集程序 → oracle：三限触发时返回结构化 Y-R0104 而非 OOM/挂死（wasmtime StoreLimits 模式：分配累计追踪、防内存抖动）。

corpus 策略照抄 wasmtime：每目标独立 corpus 仓库，OSS-Fuzz/CI 长跑，最小化测试用例一键复现。

### 4.3 差分测试的配置合法化

双引擎比较前必须 **legalize**（wasmtime 经验）：浮点 NaN 位型 canonical、Map 迭代序已由决策 36 固定为插入序（天然可比）、随机种子注入两引擎一致。非确定源必须显式列举成白名单而不是逐案修。

## 5. 稳定性、健壮性与隔离安全（运行时语义）

### 5.1 资源三限 = 唯一的「恶意的用户代码」防御面（VM 层）

| 限 | 触发 | 结果 | 证据来源 |
|---|---|---|---|
| 内存 | 堆分配超 `VmConfig.memory_limit` | `Y-R0104` 结构化错误，VM 存活可复用 | QuickJS `set_memory_limit` + wasmtime StoreLimits |
| 指令预算 | 每指令计数超限（掐 `while(true)`） | 同上 | Luau/Extism fuel；14 号已定 |
| 栈深 | 调用深度超限 | 同上 | Python 1000 帧先验；决策递归栈上限 |

三限触发必须是**廉价检查**（解释器主循环内联），且触发后 VM 实例进入可观测的 `Exhausted` 态而非崩溃——**错误也是数据**原则在运行时的投影。

### 5.2 panic-free 契约（决策 60）

- VM/typeck 编译器侧：任何 Rust panic = `Y-I` 缺陷。开发期 Miri + fuzz 拦截；运行期 `catch_unwind` 兜底转换为 ICE 上报（含最小复现引导），**绝不把 panic 泄漏成宿主进程崩溃**；
- 插件侧：Yoru 程序**没有能触发 panic 的路径**——溢出/越界/nil 全是结构化 `Y-R` 错误进 `Result` 语义或可捕获的运行时错误；宿主函数 panic 由桥接层 `catch_unwind` 转为 `Y-H` 错误（阶段 4 退出标准）。

### 5.3 隔离模型：默认拒绝 + 纵深三层

Wassette/Wasm 的「默认拒绝能力系统」与 MOSN 实践确认的沙箱不变量，投影到 Yoru 宿主引擎：

1. **语言层**：无指针、无 `unsafe` 面、值语义无共享可变 → Yoru 程序结构上无法触及宿主内存（等价于 wasm 线性内存的隔离保证，但由类型系统免费给出）；
2. **VM 层**：每实例独立堆（arena）+ 三限 + 快照分叉；实例崩溃（不可恢复 Y-R 后宿主选择终止）不影响其他实例与宿主；
3. **桥接层**：能力即参数——**没注册的能力在语言里不存在**（不只是拒绝调用）；文件牢笼/SSRF 守卫/参数硬夹在宿主桥实现（FluxDown 已验证的形态），Yoru 文档明确「策略层宿主负责」的边界（14 号结论重申）。

爆炸半径分析：即使插件完全恶意，可造成的影响 ⊆ {消耗自己实例的三限资源、调用已注入能力、返回错误数据}——与 Wassette「安装的插件拿不到 SSH 密钥」同级。

### 5.4 监督与自愈（决策 61）

Erlang/OTP 监督树的 30 年生产验证，取**最简投影**（Yoru 无进程树，宿主持有实例池）：

- **one-for-one 重启**：插件实例崩溃/熔断后，宿主重建实例（值语义 + 无状态 = 重启即干净态，BEAM 状态迁移复杂度已被语言设计消除）；
- **重启强度限制**（MaxR/MaxT）：时间窗内重启超限 → 实例进入 `Disabled` 并上报（与 16 号熔断器 `CIRCUIT_BREAKER_THRESHOLD` **统一为同一机制的两级**：连续错误=熔断禁用，重启风暴=强度熔断），OTP 文档的调参纪律（burst 与 sustained 分开考虑、多层级避免同值）写进宿主指南；
- **let-it-crash 的正确边界**：Yoru worker 代码只写 happy path（错误全走 Result），恢复是宿主监督者的职责——worker 内不写防御性样板。这同时是 AI 生成友好性（更少错误处理分支 = 更少错误机会）与健壮性的一致解。
