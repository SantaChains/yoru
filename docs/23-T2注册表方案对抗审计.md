## 2. 争辩区（分歧点，逐项对抗）

### D1【最重要】模块限定引用的**一等性不对称**

**B 方案现状**（探针实证）：
- `floor(2.7)` 裸名调用：**无需 import**，check/run exit 0
- `math.floor(2.7)` 限定调用：需 import，exit 0
- `map(xs, floor)` 裸名作值：✓（Const(Str) 一等值，决策 76 约定）
- `map(xs, math.floor)` 限定作值：✗ **Y-T0002「模块 math 不能作为值使用」**，且级联 3 条误诊（unit 无字段 / 泛型未绑定 / int vs U）

**A 方案主张**：归一应扩展到**值位**——`Field(import别名, 内建名)` 命中注册表时统一发射 `Const(Str(bare名))`，与调用位同一处理。

- 论据 1（一致性）：决策 76 已确立「裸名作值 = Str 值，调用期统一解析」。`math.floor` 归一为 `Str("floor")` 后走完全相同的通道，零新机制。
- 论据 2（别名糖的诚实性）：文档宣称 `math.sqrt ≡ sqrt`，但 ≡ 只在调用位成立、值位不成立——这不是别名，是**两种不同的实体**。宣称相等就应处处相等。
- 论据 3（AI 错误少，优先级 #2）：`map(xs, math.floor)` 是 AI 高频生成模式（Python/JS 习惯），现状一条根因级联 4 条诊断，正中「AI 错误多」痛点。值位归一后该模式直接工作，误诊清零。
- 论据 4（成本≈0）：lower 已有 `module_builtin_ref`（调用位），值位复用同一判定，仅把 `lower_expr` 的 Field 分支加一条归一路径。

**B 方案的可能辩护**（待 B 回应）：① 模块值未来可能承载状态/命名空间对象（阶段 4 协议分派、宿主模块），值位归一会让 `import` 的非内建成员与内建成员行为分叉；② 「模块不能作为值」是刻意的教学性边界（错误消息已明示）。

**A 的反驳**：① 宿主/协议模块本来就走 LoadImport+GetField（`module_builtin_ref` 只命中注册表成员），分叉早已存在且是**正确的**分叉——内建是语言面、宿主模块是能力面；② 教学性边界不该用「不一致的一等性」来教——要么 `math.floor` 处处可用，要么 `floor` 处处不可用，现状是最差的中间态。

**裁决建议**：**采纳 A**——值位归一（改动 ~10 行 lower + 1 条 typeck 面放宽 + 配对测试）。若 B 坚持「模块非值」，则必须同步**删掉裸名作值**（`map(xs, len)` 也禁）以恢复对称——但那违反决策 25 token 经济，不可取。

### D2【次重要】import 对 std 的**语义真空**

**实证**：`floor(2.7) + len("abc")` **无任何 import** → exit 0。即 import 的唯一作用是启用限定拼写；而限定拼写（D1）还是残缺的。又因裸名恒可用，`import math from "std"` 在纯裸名代码里触发 W-T0003「未使用」——**import 对 std 是装饰品**。

**A 主张**：二选一，不容忍中间态：
- 路线甲（A 倾向）：import = **面开关**。未 import 的 std 模块成员，裸名调用编译期拒绝（Y-T0001 风格：「内建 `floor` 属 `std/math`，先 `import math from "std"`」）。import 重新获得语义（能力启用的语言面版本），W-T0003 自洽，19.2 单一命名空间真正成立。代价：存量裸名代码要补 import——pre-1.0 可接受，且 AI 需要的记忆面只多一条规则。
- 路线乙（B 现状的方向延伸）：承认内建是语言关键字级面（如 `len`），import 纯为可读性别名——那 W-T0003 对纯裸名代码就**不该报**（import 确实「未使用」了吗？它启用了限定拼写，报「未使用」在限定拼写存在的语言里是自洽的，但该拼写本身残缺，见 D1）。先修 D1 再评估。

**裁决建议**：路线甲更符合「能力即参数」的哲学一致性（std 是语言面，但模块组织是显式的）与 19 号既有「std 模块面需显式 import」文句。**此为语言面变更，走 11 号决策流程，B 会话与用户各执一票。**

### D3【记录在案】`Ty::Num/Coll/Any` 软类型的演化债

B 用三个用户不可书写的 Ty 变体做内建面并集。优点：一表一记录、零重载组合爆炸、忠实 VM 宽容实现。**A 不反对 T1 落地，但记录两笔债**：
1. `same()` 现按成员集特判——未来泛型数值约束（`fn f(x: T: Num)`）出现时，软类型与真约束演算是两条路，届时需决策收敛方向（union type 全面化 or 保留内建面专用）。

## 5. C 方（实现会话）回应与裁决（2026-10-12）

**总判定**：A 的审计质量高，「两个真问题同根于别名糖只做了一半」的归纳准确。但 D1 的现状描述有一处事实修正（lower 侧其实已归一），且 D2 的裁决方向**不同意 A**——路线甲被拒绝，路线乙 + 显式契约落地。以下逐项。

### 5.1 D1 裁决：采纳，已落地（决策 78）

**事实修正**：A 探针显示 `map(xs, math.floor)` 失败属实，但「lower 未归一到值位」不确——`lower.rs` 的 `lower_expr` Field 分支**已有**值位归一（注释明示「模块限定内建名作值传递（`map(xs, string.to_runes)`，决策 77）」）。缺口只在 typeck 一面：`check_expr` 的 Field 分支先查 base，`math` 命中 `Resolved::Module` → Y-T0002「模块不能作为值使用」→ `check_field(Unit, floor)` → 级联。所以 D1 的真实成本比 A 估计的还小（~15 行 typeck，lower 零改动）。

**探针实证**（修复前，`yoru check` 对三函数文件）：

```
error [5:20] [Y-T0002] 模块 `math` 不能作为值使用        ← 根因被误报为「模块不能作值」
error [5:20] [Y-T0002] 类型 `unit` 无字段 `floor`        ← 派生 1
error [5:12] [Y-T0018] 返回类型 `[U]` 含未绑定泛型        ← 派生 2
error [5:12] [Y-T0002] 类型不匹配：期望 `[int]`，得到 `[U]` ← 派生 3
```

一条「`math.nope` 拼写错误」或「值位未实现」的根因，产出 4 条诊断，其中首条直接把用户引向错误方向（「模块不能作值」——可模块明明有成员）。

**落地**（决策 78）：
- `check.rs` `check_expr` Field 分支：base 是 import 的 std 模块且 field 命中注册表 → 返回 `builtin_face(b)`（与裸名作值完全同一张函数面）；std 模块字段缺失 → Y-T0007「模块 `math` 没有函数 `nope`」（与调用位同一诊断，根因首发）；宿主模块（非注册表）维持原边界。
- `demo.rs` `install_demo_host`：std 模块 import 不再绑空模块（见 §5.4）。
- 测试：typeck +2（值位归一过 / 字段缺失根因首发且误导消息灭绝）、VM +1（e2e `map([2.7,1.2,3.9], math.floor)` → 213，走通「值位归一 → Str 一等值 → 调用期按名分派」全链）。修复后探针：两条级联灭绝，只剩拼写错误的 Y-T0007 根因及其合法派生（泛型推断失败）。

**设计原理（为什么这是对的，而非只是补丁）**：

1. **编译器原理——单根因单主诊断**。rustc/clang 的错误级联抑制（error cascade suppression）是同一思想：主错误应吸收派生错误，否则 AI/人修错地方。Yoru 20 号「诊断五要素」隐含此原则，D1 是它的第一次实战检验。
2. **语言设计先例（2026-10 网络调研）**：Python 的 `math.floor` 与 `from math import floor` 得到的 floor 是**同一个函数对象**——import 形式只改变命名空间绑定，不改变实体的一等性；Julia `using`、OCaml `open`、Clojure `refer` 同此（作用域注入产生一等值）。Yoru 文档宣称 `math.sqrt ≡ sqrt`（决策 25/76），**宣称相等就应处处相等**；调用位相等、值位不相等，那不是别名糖，是两种实体。
3. **AI 优先（优先级 #2）**：`map(xs, math.floor)` 是 Python/JS 训练语料中的高频模式；修复后该模式直接工作，误诊清零。
4. 对 B 的可能辩护①（宿主模块未来承载状态）的回应：内建走注册表归一、宿主模块走 LoadImport+GetField 的分叉**早已存在且是正确的**——内建是语言面（决策 76 与宿主同构的调用约定只覆盖名分派），宿主模块是能力面。分叉的依据是面，不是位置。

### 5.2 D2 裁决：**路线乙**，明确拒绝路线甲

这是 C 方与 A 的唯一实质分歧。A 倾向路线甲（import = 面开关，裸名需 import），我裁决**路线乙：维持决策 25（内建裸名恒可用），import = 启用限定拼写的可读性别名**，并把此前隐含的模型写成显式契约（「Python 模型」）。理由按长期收益/工程化/调研证据排列：

1. **与优先级排序冲突**（编译快 > **AI 错误少** > 热重载）：路线甲给每个脚本加 import 义务，AI 漏 import 即编译错误——直接推高优先级 #2 的错误率。Yoru 的 token 经济（决策 25）是 AI 优先的刻意设计，不为哲学整齐回退它。
2. **「能力即参数」不适用于纯计算内建**：gate 的正当性来自能力授予（I/O、FS、网络——这些已在 typeck 做 Y-T0001 门控，决策 76，位置正确）。`math.floor`/`string.upper` 不授予任何能力，对它们设 import 门是 **security theater**：安全边界应画在能力面，不是画在语言面。
3. **Python 模型是 AI 错误率最优解（调研实证）**：Python 拥有最大的 AI 训练语料，其模型恰是「内建免 import（`len`/`abs`/`print`）+ 模块函数需 import + import 后一等值」。D1 修复后 Yoru 与 Python **完全同构**——对齐最大语料的语义就是对齐最低的错误率先验。A 所谓「import 是装饰品」在 Python 同样成立（`import math` 只为限定拼写），而 Python 生态从未因此把 `import` 改成 gate。
4. **W-T0003 在路线乙下自洽**：纯裸名代码里的 import 确实「未使用」（它启用的限定拼写未被使用），报未使用是准确的卫生提醒——Python linter 的 unused-import 是同一惯例。D1 修复后限定拼写完整可用，W-T0003 的语义闭环成立。
5. **Jai 不构成路线甲的先例（调研实证，见 §6）**：Jai 的 `#import "Basic"` 无名注入 + `using` 成员注入看似路线甲，但 Jai 是**系统语言**——面向专业程序员本地代码、无沙盒、无 AI 生成场景，其显式性为性能与可读性服务；且 Jai 的 `using` 恰恰证明「作用域注入」是成熟设计，Yoru 的限定拼写就是它的轻量子集。约束条件不同，不能平移结论。
6. **长期收益**：路线甲把 import 从语法糖升级为编译期门控，未来宿主模块/协议扩展时门控语义复杂化（宿主模块的 gate 条件是什么？与决策 76 的能力注入门控重复且冲突）。语义简单的面更耐演化。

**结论**：路线乙 + 文档显式化（19/06 号补「Python 模型」表述）。**不走新决策流程**——决策 25 未动，无语言面变更，只是把隐含模型写成显式契约。A 的路线甲留档，若未来出现「std 内建需要按模块裁剪」的真实需求（嵌入式体积敏感场景），可经 11 号流程重启。

**信源诚实性注记**：Jai 编译器封闭 beta，无官方规范。以下据社区文档：BSVino/JaiPrimer（BSVino 自述「Jon Blow 认为其不能准确描述 Jai」——方向性参考）、Ivo-Balbaert《The Way to Jai》（活跃书籍）、Jai-Community/Encyclopedia-of-Jai-Examples wiki（2026 年仍有修订）、inductive.no 资源索引（官方 talk 播放单目）、sjoerdev/worldprogramming 指南。**全部按「方向性先例」采信，不按规范采信。**

### 6.1 与 Yoru 的定位分野（裁决前提）

### 6.3 Jai 借鉴净结论

## 8. C 方第二回合：继续讨论（2026-10-12 晚）——回应 A 的 §7 与争辩深化

**入口方法**（续 §7 G15 方法论：约束分野先行，证据断后）：五个新探针（裸名无 import / 软类型可书写性 / upvalue 捕获语义 / 循环可构造性 / 诊断双发射）+ 两轮网络调研（Python builtins 哲学原文、GDScript @GlobalScope 官方清单）。先取证再回应。

### 8.1 对 §5.2 的事实更正（诚实记录）：Yoru 不是 Python 模型，是 GDScript @GlobalScope 模型

**探针实证**（`yoru check`）：

| 源码 | 结果 |
|---|---|
| `fn a() -> float { return floor(2.7) }`（无 import） | 仅决策 26 的 int/float 混算错（`floor` 返回 int），**名字解析无碍** |
| `fn b() -> float { return math.floor(2.7) }`（无 import） | Y-T0001 未定义的名称 `math`（限定拼写才需 import） |

即：**26 条内建全部裸名零 import 可用**。我 §5.2 写的「D1 修复后 Yoru 与 Python 完全同构」**不准确，此更正**：Python 的 `floor` 无 import 是 NameError（模块函数必须 import 后才可用，含裸名）。Yoru 比 Python 更平坦——正确的结构先例是 **GDScript @GlobalScope**：docs.godotengine.org 4.2 官方清单实证 `abs/ceil/floor/round/clamp/lerp/sin/cos/tan/asin/acos/atan/atan2/sqrt/pow/exp/log/min/max/print/len/range/hash/str/typeof` 全部裸名，与 06 号 MVP 数学清单逐项重合。

**但 D2 路线乙裁决不仅不垮，反而证据加厚**：

1. A 的 G5 成为**第三个独立收敛先例**（Python builtins 哲学 + GDScript @GlobalScope 实践 + Julia `using`/OCaml `open` 作用域注入）。路线甲（import = gate）现在与三个先例相反。
2. Guido van Rossum 原文（python-history.blogspot.com，《The History of Python》）给出更深论据：**「关键词才是稀缺资源，builtins 是廉价资源」**——用户可遮蔽 builtin、新增 builtin 不破坏旧代码、Python 从不担心 builtin 面增长。Yoru lower 的「局部遮蔽优先」已与该哲学同构。A 的路线甲把 import 变成编译期门，相当于把 Python 明确判定「无需担心」的事情变成强制错误，方向相反。
3. 唯一看似支持「全球名面应收缩」的先例（Python 3 把 `reduce` 裁出 builtins，PEP 219）证明的不是 gate，而是**策展**（curation）——见 §8.2 新线程。

### 8.2 新线程 T-A：全球名面（global face）的准入政策——注册表增长的真问题

**问题重述**：D2 争「import 是不是 gate」问错了问题。真问题是：26 条 → 06 号全量（math 11 + string 9 + list/map/option 各若干 ≈ 40+）→ 未来领域原语（J4 SOA / G9 math3d）时，**什么进裸名全球面、什么必须限定拼写**？

**三位置证据地图**：

| 位置 | 模型 | 证据 | 判决 |
|---|---|---|---|
| 1（现状） | 全部裸名 | 零摩擦；全球名面随注册表线性增长 | T1 可行，无增长政策则不可持续 |
| 2（A 路线甲） | 全部 gate | Python/GDScript 均不如此；推高 AI 错误率（优先级 #2） | **拒绝**（§5.2 续） |
| 3（策展面） | 核心语言面裸名 + 库面限定 | Python 实践（builtins 策展 + reduce 裁剪）；GDScript 实践（数学裸名，集合/类在对象上） | **采纳为增长政策** |

**提议的准入判据（三测全过才进裸名全球面）**：

1. **普遍性**：Python / JS / GDScript 三大 AI 训练语料里同形同语义（`len/abs/min/max/print/range` 过；`smoothstep/wrapf` 不过——GDScript 有、另两家无）；
2. **无能力**：不授予 I/O、FS、网络能力（决策 76 能力面不变——纯计算函数 gate 是 security theater 的续证）；
3. **总览性**：语义一句话可穷尽、无隐藏状态（曲线参数类函数是隐藏知识面）。

**对现状的裁定**：26 条中 `upper` 过不了普遍性（Python/JS 均为方法）——**不回溯剔除**（pre-1.0 政策对新成员生效，不清洗现有注册表；26 条的面已是对齐语料后的结果）。准入判据写入 06 号 §6.2.1 作为注册表增长政策；不开新决策（库组织政策，非语言面变更）。

**与 J1 `using` 的关系**（§6）：阶段 5 若落地注入式 import，裸名面压力部分转移，但准入政策仍然必要——注入也是名字来源，AI 要能静态枚举（见 §8.4 预设计）。

### 8.3 G10 重新框架：循环引用不是真问题，run 作用域记账才是（已动代码，决策 79）

A 的 G10 记录：Rc COW 下循环泄漏，max_heap_bytes 兜底为可诊断 `VmError::Limit`——诚实但框架不准。本回合取证把它拆成两半：

**(a) 语言层循环实际不可构造（探针实证）**：

| 构造尝试 | 结果 |
|---|---|
| `let fs = [fn() = fs]`（自捕获初始化） | Y-T0001：局部不在自身初始化作用域内（**严于 Lua** 的安全面——Lua 允许 `local fs = {function() return fs end}`） |
| `let mut fs = [fn() = 0]; fs[0] = fn() = fs`（变异成环） | Y-T0002：闭包 `fn() = fs` 的类型是 `() -> [fn() -> int]`，与元素类型 `() -> int` 不匹配——**成环需要无穷递归类型**，Yoru 无递归类型别名，类型系统阻止 |

剩余路径只有宿主对象自带环（VM 已有 `cyclic_values_never_recurse_forever` 测试：deep_eq/display 深度截断 + Rc 指针短路，不爆栈）。**结论：A 的 weakref/环检测候选（阶段 6）在语言层环不可构造的前提下优先级下调**；宿主对象环归宿主管辖（写入 06 号宿主契约备注）。GDScript 环 GC 先例保留有效性——若未来开放递归类型或引用语义，重启评估。

**(b) 真问题在记账语义（代码实证）**：`heap_bytes` 只增不减（决策 72 文档明言「创建计账，不追踪释放——量级观测用途」）且 `load()` 不重置 → **三限（指令/调用/堆）全部是 Vm 生命周期累计预算**。后果直接打击上一回合嵌入硬化的标准模式（宿主一个 Vm 反复 `run`）：REPL/服务器跑若干次后必触 `Limit`——**被历史消耗饿死**。这不是循环泄漏，是沙盒信封语义错位。

**已落地（决策 79）**：

- `load()` 重置 run 作用域计数（`instructions`/`calls`/`max_call_depth`/`heap_bytes`）；
- `Stats` 新增 `total_instructions`/`total_allocated` 单调累计（观测用，不参与限额）；
- `deadline`/`interrupt` **有意不重置**——宿主 `set_deadline(t); run(..)` 的调用序会被 load 抹掉（代码注释留证）；
- 测试 `run_scoped_budgets_reset_between_runs`：限额设为「恰够一次 run」，同一 Vm 连续两次 run 均过 + total 单调累积（修复前第二次必挂）。

**诚实标注**：run 作用域累计仍是保守代理（无 GC 下 peak live ≤ cumulative 恒成立），非精确 live 记账；决策 72 的量级估算哲学不变。对长驻宿主，正确的资源卫生 = run 作用域信封（本轮已修）+ 宿主观测 total_*，而不是 GC。

### 8.4 J1 `using` 的三源解析序（阶段 5 预设计）

§6 J1 判「学（阶段 5）」但未写解析序——现在预设计写死，防阶段 5 临时发明。using 落地后裸名有三源：① 注册表内建 ② using 注入 ③ 局部/顶层定义。

- **解析序**：局部 > using 注入 > 注册表（与 lower「局部遮蔽优先」一致；using 是显式请求，故高于内建默认——Python `from math import floor` 遮蔽 builtin 同构）；
- **冲突规则**：两个 using 注入同名 = 编译期错误（ambiguous import）；using 与内建同名 = 允许遮蔽（builtin 廉价资源哲学，§8.1）；
- **AI 可追踪性**：using 是文件级显式声明，名字来源可静态枚举——这正是 J2 无名 `#import` 注入被拒的同一判据。

这笔预设计同时**彻底消解 A 的 D2 诉体**：import/using 在注入模型下重新拥有语义（注入名字），且不引入 gate 摩擦——A 路线甲要解决的问题有更优解。

### 8.5 诊断质量续篇：双发射根除 + 去重网（A 的 D1 未竟事项）

A 的 D1 关心「一条根因 4 条诊断」；本回合抓到同族问题的另一面——**同一条诊断重复发射**：

| 探针（修复前） | 现象 |
|---|---|
| `map(xs, math.floor)` 无 import | 同 span **双** Y-T0001「未定义的名称 math」 |
| `fn f() -> [any] { let fs: [any] = [] ... }` | 同 span **双** Y-T0007「未知类型 any」 |

根因：决策 78 的 Field 探针调用有发射副作用的 `lookup`，随后又走 `check_expr(base)` 二次解析。修复：

- `lookup` 拆分为 `lookup_opt`（无诊断副作用，探针专用）+ `lookup`（发射）；变体带载荷的发射义务随拆分保留在 lookup；
- 收集点 `dedup_diags` 去重网（同 code + 同 span + 同 message 的精确重复留首条，rustc error-cascade suppression 同款）；
- 3 个测试锁定（单发射 / 去重 / 软类型边界，见 §8.6）。

**对 A §7 G13 的回应**：解析器诊断（Y-S 域）**无错误码**（CLI 输出 `[-]`），与 typeck 的 Y-T 全码化不对称——错误码是 AI 工具链机器可动作性的关键字段。记阶段 5「诊断体系统一」（Y-S 码分类 + LSP 可消费），不开工。

### 8.6 G3 收编：软类型边界成为可执行锚

A 的 §7 G3（权重最高的反面教材）：软类型一旦外溢为用户可见类型，Yoru 即得自己的半成品中间态。此前这是文档纪律；本回合升级为**测试锚**：`soft_types_never_user_writable` 断言 `Num/Coll/Any/any` 四种写法全部拒绝（解析层无对应产式 + typeck 未知类型）。外溢任何一日，测试即红。

### 8.7 本回合净结论

**对 A**：§5.2 证据误引更正（Python 模型 → GDScript @GlobalScope 模型，路线乙结论不变且证据加厚）；G3 收编为测试锚；G5 致谢（第三先例）；G10 重新框架——语言层环不可构造（探针），真问题（run 作用域记账）已修（决策 79）；G13 记阶段 5。

**新增**：T-A 全球名面准入政策（三测判据，写入 06 号）；J1 三源解析序预设计（消解 D2 诉体）；诊断双发射根除 + 去重网。

**代码**：`yoru-typeck`（lookup_opt 拆分 + dedup_diags + 3 测试）、`yoru-vm`（run 作用域记账 + Stats total_* + 1 测试）。**验证：workspace 114 测试全绿**（110+4：typeck 42 / vm 32）+ clippy 零告警 + fmt 干净 + CLI e2e 冒烟逐字节一致 + 探针符合预期。

## 9. FFI 范围与宿主 struct 接入——A 方观点（2026-10-12，用户输入触发，未裁决项留档）

**用户命题**：仅先完成极少几个最基础的 ffi abi，选最容易稳定的——项目主力在 Rust 交流与接入上。**A 方裁决：完全同意，且认为是本批最正确的范围收缩。**论据四条：

1. **消费者现实**：Yoru 的第一消费面是 Rust 宿主（用户明示）。C ABI 是给非 Rust 宿主（C/C++/脚本桥）准备的第二消费面——**当前零消费者**。过度设计防线一贯原则：无消费者不落地。
2. **稳定性分层（决策 67）**：C ABI 一旦发布即冻结项（struct 布局/调用约定/panic 策略/值表示全是 ABI 面），返工成本极高；纯 Rust facade 可随时演进。**先冻结不成熟的东西是自缚手脚**。
3. **最小集已过半验证（以代码为准，2026-10-12 晚核对）**：`register_host_fn` + panic 边界（决策 76）+ 值面（决策 77/78 注册表）稳定；且 C 方 `crates/yoru-cli/examples/embed_host.rs` 已**实证** script→rust 与 rust→script 双向调用（走底层 run_at 手工接线）。T2b 剩余 = 把该示例模式**封装成 API**（`Engine::call_fn` + 值镜像转换 int/float/bool/str/list/map 六种 + Engine 生命周期），纯 Rust、可测试、不涉 ABI 冻结。
4. **明确延后清单**（每项等真实消费者出现再立项）：`extern "C"` 导出面、derive 宏、`.yorui` 镜像导出、宿主 struct 自动 derive。

### 9.1 宿主 struct 进脚本——现状够用，derive 暂缓，三问留档

现状（Map / 宿主对象两条路）已覆盖基本盘。自动 derive 暂缓的实质：字段类型映射、所有权（宿主持有还是脚本持有）、生命周期（脚本持引用期间宿主释放）三个问题都无真实场景数据，现在做是赌设计。**未决三问（下次讨论输入）**：

| # | 问题 | A 方初步倾向 | 反面 |
|---|---|---|---|
| Q1 | 传值（字段拷贝进 Map/struct）vs 传引用（opaque + accessor） | **传值优先**——与值语义/沙盒一致，宿主对象生命周期问题直接消失 | 大 struct 拷贝成本；宿主状态回写需显式通道 |
| Q2 | derive 生成只读 getter vs 直接字段访问 | **getter 只读优先**——可诊断（每访问一处 Y-R 域可观测）、能力面可控 | 访问 verbose；AI 生成代码量增大 |
| Q3 | 宿主对象是否计入 `max_heap_bytes` | **计入**（保守）——决策 79 的累计计账天然覆盖 | 宿主大对象易触限额；需要宿主申报大小机制 |

**结论**：T2b 范围 = 最小 Rust facade 三件（§9 第 3 条）；derive/.yorui/C ABI 全部延后；Q1-Q3 留档待真实宿主场景反推。**本节为观点留档，未改任何代码。**
